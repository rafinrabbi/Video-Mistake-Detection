Why the graph does so little: the pointer saturates The step pointer advances once per no-deviation window, but a recipe step spans many windows — so it races to the last step and clamps. It first reaches the final step at a median 16% of the way through a recording, and 66% of all 23,696 test windows are conditioned on the final step. For two-thirds of the run the "graph context" is a constant naming the last step. R5 does not show structure is useless; it shows this pointer stops delivering structure early. Same failure we rejected the offline protocol for.

Open calls

worth deciding before the chain finishes, not after
R5 came back flat. Fix the pointer, or report what we have? The saturation is a bug in our method, not a property of procedural conditioning — so the current ablation measures a broken pointer. Fixing it (advance on step completion, not per window) and re-running is arguably now the highest-value experiment available, above R7 and R10: it tests the method as designed. Cost: a code change plus one full pass. The alternative is to report the saturation as a finding and scope the claim to earliness.
Are R7 and R10 still worth running? Their purpose changed when R6 landed. They no longer adjudicate detection — that is settled — so they would now decompose the earliness effect: does it need the correct plan (R7), or merely a position pointer (R10)? Interesting, no longer load-bearing. The pointer fix is better value than either.
Retrain with real rationale supervision? CaptainCook4D ships free-text error descriptions that would make the explanation claim true. Stronger paper, but a retrain plus full re-eval. Logged as future work — do not queue it ahead of the ablation.
