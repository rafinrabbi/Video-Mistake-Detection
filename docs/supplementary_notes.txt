SECTION 1 — WHY THIS PROBLEM IS HARD (motivation gap in original)
────────────────────────────────────────────────────────────────────────────────

Most video anomaly detection papers detect "something unusual happened."
This system must answer a stricter question:
  "Was the right thing done, in the right order, with the right object?"

That distinction matters because:

  - Chopping a vegetable is not an anomaly in cooking. Chopping it before
    washing it IS a procedural mistake. Generic anomaly detectors cannot tell
    the difference because they have no model of what "should" happen.

  - The same physical action (e.g., picking up a screwdriver) can be correct
    in step 3 and a mistake in step 5. Temporal context is required.

  - Mistake classes are fine-grained:
      wrong_order      — right action, wrong position in sequence
      missing_step     — a required step was skipped entirely
      wrong_object     — right action, wrong tool or ingredient
      wrong_action     — wrong technique (stir vs. fold, etc.)
      wrong_quantity   — right object, wrong amount
    A binary "mistake / no mistake" label throws away this structure.

Compared to prior work:
  MistSense  — binary online detection only, no procedural graph
  MoniTor    — training-free online VAD, detects outliers not procedural errors
  PREGO      — uses procedural graph but no uncertainty modeling
  ASK-HINT   — LLM-based, no local VLM, no adaptive threshold

This system combines all missing pieces: graph + VLM + uncertainty-aware decision.

SECTION 2 — HOW THE PROCEDURAL GRAPH IS ACTUALLY BUILT (more detail)
────────────────────────────────────────────────────────────────────────────────

Input:  a plain-text task description (e.g., "assemble a cardboard box")
Output: a JSON ProceduralGraph with:

  steps     — ordered list of what to do
  objects   — physical items needed (e.g., "cardboard_sheet", "tape")
  actions   — verbs that can occur (e.g., "fold", "press", "cut")
  states    — expected object states after each step (e.g., "flap_folded")
  edges     — directed links between steps:
                after(A, B)    = B must come after A
                requires(A, X) = step A needs object X
                produces(A, S) = step A produces state S

The builder calls GPT-4o with a structured prompt → receives JSON → validates:
  - DAG check (no cycles)
  - No dangling references (every edge endpoint exists)
  - No isolated steps (every step connected to the graph)

Fallback: if no OPENAI_API_KEY, src/vmd/graph/builder.py has a local parser
that converts a numbered list of step descriptions into a linear chain graph.
This is good enough for testing but produces weaker prompts.

Current local graphs (already built):
  blacklight   8 steps   electronics repair
  cardboard   14 steps   packaging/box assembly
  electronics  8 steps   electronics assembly
  ion          9 steps   chemistry/lab procedure
  tsumiki      7 steps   toy construction

SECTION 3 — WHAT THE VLM PROMPT ACTUALLY CONTAINS (missing from original)
────────────────────────────────────────────────────────────────────────────────

For every 4-second window the model receives:

  [1] Task name                    e.g., "Assemble cardboard box"
  [2] Current expected step ID     e.g., "step_03"
  [3] Current step description     e.g., "Fold both short flaps inward"
  [4] Valid next steps             list of step descriptions that can follow
  [5] Required objects for step    e.g., ["cardboard_sheet", "hands"]
  [6] Expected states after step   e.g., ["short_flap_folded"]
  [7] Valid variations             e.g., ["fold left flap first OR right first"]
  [8] History summary              last 3 predictions: action | deviation | class

  + the sampled video frames (1 fps = 4 frames per 4-second window)

The VLM must return strictly:
  {
    "observed_action":     "what the person is doing",
    "observed_objects":    ["object1", "object2"],
    "step_id":             "step_03",
    "deviation":           true or false,
    "mistake_class":       "wrong_object",
    "confidence":          0.0–1.0,
    "uncertainty_reason":  "occlusion",
    "rationale":           "short explanation",
    "expected_vs_observed": "expected X, saw Y"
  }

Why structured JSON matters:
  Unstructured free-text VLM output cannot be parsed reliably into metrics.
  JSON forces the model to commit to a class, a confidence, and a reason.

SECTION 4 — UNCERTAINTY IN DETAIL (formula explanation)
────────────────────────────────────────────────────────────────────────────────

The system uses two uncertainty signals combined into one score.

Signal 1 — verbalized confidence
  The VLM outputs a float in [0, 1].
  Low confidence = model is unsure visually.
  Contribution: 0.6 × (1 - confidence)

Signal 2 — uncertainty reason penalty
  The VLM also names WHY it is uncertain. Each reason has a penalty:
    none              → 0.00  (model is confident, no issue)
    valid_variation   → 0.15  (action is valid but unusual)
    ambiguous_action  → 0.25  (hard to tell what action is)
    short_clip        → 0.20  (4-second window too brief)
    occlusion         → 0.30  (hand/object blocked from view)
    weak_graph_match  → 0.40  (graph step does not match video well)
  Contribution: 0.4 × reason_penalty

Combined:
  uncertainty = min(1.0,  0.6 × (1 - confidence)  +  0.4 × reason_penalty)

Additionally, history_inconsistency measures flip-flops in recent predictions:
  If the last 3 windows alternate deviation=True/False/True, that is suspicious.
  High inconsistency raises the threshold → system waits for more evidence.

SECTION 5 — ADAPTIVE THRESHOLD IN DETAIL (most novel part of the system)
────────────────────────────────────────────────────────────────────────────────

The threshold τ determines: "how confident must the model be to declare mistake?"

Fixed threshold (baseline): τ = 0.5 always.
  Problem: a step with many valid variations (e.g., "add spice in any order")
  should tolerate more ambiguity. A step with one strict order should not.

Adaptive threshold (contribution B):

  τ = sigmoid( α × complexity
             + β × (1/num_variants)
             + γ × uncertainty
             + δ × (1 - graph_confidence)
             + ε × history_inconsistency
             + bias )

  Where:
    complexity        = num_steps / 20        (longer task → more room for error)
    1/num_variants    = inverse variant count  (fewer alternatives → stricter)
    uncertainty       = composite score above  (more uncertain → higher τ)
    1-graph_conf      = graph quality penalty  (weak graph → higher τ, less trust)
    history_incons.   = flip-flop rate         (unstable predictions → wait longer)

  sigmoid maps the linear combination into [0, 1].

  Parameters [α, β, γ, δ, ε, bias] are fitted via logistic regression
  on the validation set per-window predictions (features → true_label).
  Script: scripts/03b_fit_threshold.py

SECTION 6 — ONLINE vs OFFLINE DISTINCTION (why it matters for the paper)
────────────────────────────────────────────────────────────────────────────────

Online evaluation (causal):
  - The system processes clip windows one by one, left to right.
  - The step index only advances forward when no deviation is predicted.
  - No peeking at future windows.
  - This matches real-world deployment (live monitoring).
  - Metric emphasis: low latency to detection, early detection score (EDS).

Offline evaluation (non-causal):
  - All windows of the video are available at once.
  - Step index assigned by position, not by causal state machine.
  - This is an upper bound on what the system can achieve.
  - Metric emphasis: F1, AUC, class precision/recall.

Both are reported side by side. The gap between online and offline F1 shows
how much performance is lost by the causal constraint.
Paper framing: MistSense/MoniTor are online only. Reporting both positions
this work as a more complete benchmark.

SECTION 7 — LORA FINE-TUNING PLAN (Phase 4, not yet run)
────────────────────────────────────────────────────────────────────────────────

The zero-shot baseline uses a frozen Qwen2.5-VL-7B.
Phase 4 fine-tunes it with LoRA (Low-Rank Adaptation):
  - Adds small rank-16 to rank-64 matrices to attention + MLP layers.
  - Only adapter weights are trained (~0.1% of total params).
  - Full model stays frozen → fast training, low memory.

Loss function is a combination of:
  CE loss     — predict correct mistake class
  Calibration loss (NLL) — force confidence to match actual correctness rate

Why calibration loss matters:
  Zero-shot baseline ECE is ~0.77 (very poorly calibrated).
  If the model says 0.82 confidence but is wrong 60% of the time,
  the adaptive threshold cannot work correctly.
  Training with calibration loss brings ECE closer to 0.0.

Training setup:
  Data:      EgoOops train split (30 videos)
  Hardware:  A100/H100 80GB
  Precision: bf16 + gradient checkpointing
  Time:      ~24–48 hours estimated
  Script:    scripts/03_lora_train.py

SECTION 8 — METRICS EXPLAINED (for presentation)
────────────────────────────────────────────────────────────────────────────────

binary F1
  Precision and recall of "is there a mistake in this window?"
  Current: ~0.32 (weak baseline, room to improve with LoRA)

macro F1
  Average F1 across all mistake classes equally weighted.
  Current: ~0.17 (very weak — model rarely classifies the right type)
  This is the hardest metric and the main research target.

AUC-ROC
  How well does the raw confidence score rank mistake vs no-mistake windows?
  Current: ~0.60 (slightly above random = 0.5, not great)

ECE (Expected Calibration Error)
  Does the model's confidence match its accuracy?
  0.0 = perfectly calibrated, 1.0 = completely wrong.
  Current: ~0.77 = very miscalibrated. Key problem to fix in Phase 4.

Brier score
  Mean squared error between predicted probability and true label.
  Lower is better. Combines sharpness and calibration.

Start-time MAE
  For offline evaluation: how many seconds off is the predicted
  mistake start time compared to ground truth timestamp?
  Lower is better. Only computed when a mistake is correctly detected.

EDS (Early Detection Score)
  Rewards detecting a mistake early, before it compounds.
  A system that catches the mistake 2 seconds in scores better than
  one that catches it 8 seconds in, even if both are correct.

SECTION 9 — ABLATION TABLE (what 04_full_eval.py should produce)
────────────────────────────────────────────────────────────────────────────────

The final paper table compares four system configurations:

  Config A — no graph, fixed τ
    Plain VLM prompt with no step/object/state context.
    Fixed threshold τ = 0.5.
    Represents: generic VLM baseline.

  Config B — graph, fixed τ
    Graph-conditioned prompt.
    Fixed threshold τ = 0.5.
    Isolates: contribution of Approach A (graph reasoning) alone.

  Config C — graph, adaptive τ (fitted)
    Graph-conditioned prompt.
    Adaptive threshold with fitted params from 03b_fit_threshold.py.
    Tests: both contributions together (zero-shot).

  Config D — graph, adaptive τ, LoRA fine-tuned
    Full system after Phase 4 training.
    Expected: best results. This is the target for the paper.

B vs A isolates the graph contribution.
C vs B isolates the threshold contribution.
D vs C isolates the LoRA fine-tuning contribution.

SECTION 10 — KNOWN ISSUES AND NEXT ACTIONS
────────────────────────────────────────────────────────────────────────────────

1. scripts/04_full_eval.py does not load fitted threshold params.
   Fix: AdaptiveThreshold.from_json("outputs/threshold_params.json")
   Priority: HIGH — must fix before ablation run.

2. Zero-shot ECE = 0.77 is very high.
   Root cause: frozen VLM is not calibrated for this task format.
   Fix: Phase 4 LoRA with calibration loss.

3. Macro F1 = 0.17 means mistake class prediction is near-random.
   Root cause: frozen model rarely gets fine-grained class right.
   Fix: LoRA fine-tuning with CE loss over all 6 classes.

4. Online == offline performance in current results (identical F1).
   This is suspicious — the causal online protocol should score lower.
   Root cause possibly: step index advances too aggressively (steps forward
   even when deviation could have moved step back).
   Needs investigation before paper submission.

5. graph_confidence is currently hardcoded to 0.8 in both online.py
   and offline.py. Phase 4 should make this dynamic based on actual
   validator output (how many edges were grounded to EgoOops vocabulary).
